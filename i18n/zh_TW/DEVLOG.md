## 關於主題選擇

> 本節中的「筆者」指 workshop 的最初開發者（以下簡稱「開發者 A」）。內容寫於初期開發階段，用來記錄專案立項時的各項考量。

開發隊式 workshop 的第一個挑戰就是選題：究竟要以什麼作為專案主題？這對隊式 workshop 而言相當棘手。

### 選題目標

對於選題，我希望達到的目標有以下三點：

+ **R1：** 專案必須足夠小，讓幾乎只有 C89 與 C++98 基礎的同學能在一週的課餘時間內完成；積極的同學甚至可以每天完成當天的作業。
+ **R2：** 專案應盡可能涵蓋暑期培訓隊式部分的重要知識，達到練習課程內容的目的。
+ **R3：** 專案必須貼近實際需求。即使提出的解法不是最佳方案，也至少要大致符合可接受的軟體工程慣例，避免對學生造成誤導。這一點至關重要，也長期困擾著筆者，後文會再說明。

### 縮小範圍與重新界定問題

隊式 workshop 選題最大的難題，在於必須涵蓋龐大的內容。暑期培訓的隊式部分需要講解 C\# 語法、物件導向程式設計、多執行緒、非同步、gRPC、Avalonia、Unity、現代 C++ 等眾多主題；想用一個讓幾乎只有 C89 與 C++98 基礎的同學能在短短一週課餘時間內完成的小專案涵蓋全部內容，幾乎不可能。若專案包含網路通訊、跨語言等所有內容，規模必然不小；若規模足夠小，又很難涵蓋所有內容。因此，第一步就是做出適當取捨。

現代 C++ 是第一個被捨棄的主題。其餘內容大多能以單一 C\# 技術堆疊完成，額外加入 C++ 章節只會徒增負擔。由於眾所周知的原因，建置符合工程需求的 C++ 環境本身就相當耗時，違反 **R1**；同學完全可以透過額外的小作業，或在日後的隊式開發中熟悉這套環境。如果未來確實需要 C++ 章節，也可以在主題確定後，於通訊章節加入一個 C++ CLI 用戶端，與 Avalonia 用戶端並列；就像 [Kubernetes](https://kubernetes.io/) 提供 `kubectl` 與多種語言的 API，這個用戶端可用任何合適的語言撰寫。

其次，雖然專案需要訓練 Avalonia 技術，選題時卻不必特別受它限制；無論最後開發哪一類軟體，都能加入「製作 GUI 用戶端」這項需求。因此，只要確定主題後再配合調整 Avalonia 部分即可。Unity 也類似，只要為軟體製作一個生動、有趣且可遊玩的用戶端。

C\# 語法不必特別考量，只要選用 C\# 作為開發語言，就一定會得到練習。gRPC 提供非同步介面，因此採用 gRPC 也會自然帶入非同步程式設計。物件導向程式設計同樣容易融入；[物件導向設計模式](https://zh.wikipedia.org/wiki/设计模式_(计算机)) 是前人整理的成熟經驗，雖然可能被濫用，但只要不是為用而用，仍是很好的參考。幾乎任何軟體都能採用合適的架構來練習物件導向思維。因此，問題縮小為：找出一個能自然容納多執行緒與 gRPC 的題目。

但光是同時容納多執行緒和 gRPC 這兩項知識點就已經讓我頭痛。

### 曾考慮過但被否決的選題

先從多執行緒談起。在暑期培訓中，我們希望讓大家接觸較底層的執行緒同步問題，例如管理執行緒，使用互斥鎖、條件變數（或監視器）與號誌進行同步和互斥，以及處理生產者—消費者問題等；但要為這些內容設計自然的情境並不容易。多執行緒最常見的用途之一，是以平行運算加速工作；然而，現在已有許多高效能平行運算程式庫，若仍手動管理執行緒與同步互斥，通常並不明智，也嚴重違反前述 **R3**。雖然手動管理執行緒如今已不常見，我仍希望找到一個至少合理的應用情境。

有人或許會問：為什麼不做一款簡單遊戲，讓每個執行緒控制一個角色？原因很簡單——幾乎所有遊戲引擎都不是這樣運作的。一般遊戲會在統一的更新迴圈中依畫面更新率處理每一幀，完成所有實體的運算，而不是以一個執行緒控制一個實體。多執行緒可能出現在個別運算步驟中，但那主要屬於平行運算，又回到上一段的問題。因此，以遊戲作為這項練習的情境同樣違反 **R3**。

也有人可能會問：為什麼不把既有隊式開發中需要執行緒同步的情境移植到這個 workshop 專案？目前隊式開發使用執行緒同步的部分主要有以下幾種：

+ 第一是通訊部分。伺服器需要以執行緒同步處理 gRPC 要求，但多執行緒課程安排在通訊之前，不能與 gRPC 綁在一起。另一方面，用戶端選手介面接收伺服器傳來的遊戲資訊並更新狀態時，也要透過互斥避免與選手程式碼發生資料競爭；這不僅與 gRPC 耦合，所需處理的競爭情況對小型專案而言也過於龐雜，嚴重違反 **R1**。
+ 第二是下載器。它可能需要平行下載小檔案，但這會要求同學自行租用雲端儲存，顯然不可行。
+ 第三是遊戲引擎。隊式目前（截至 2026 年春）的遊戲引擎，是本 workshop 最初的開發者（也就是本段的筆者）以 [THUAI3.0](https://github.com/eesast/THUAI3.0) 為基礎大幅重構與修改，在 [THUAI4](https://github.com/eesast/THUAI4) 完成基礎設計，再於 [THUAI6](https://github.com/eesast/THUAI6) 加入狀態轉移機制而成；但前兩版存在嚴重的設計錯誤。THUAI3.0 為每個遊戲實體建立一個計時器 `Timer`，THUAI4 更進一步改成每個遊戲實體各有一個執行緒 `Thread`（THUAI9 的開發者似乎又改成每個實體各有一個 `Task`，造成更大的問題）。這正是前文所說的情況：遊戲邏輯應依畫面更新率統一控制，筆者當初卻因不熟悉原理而為每個實體建立執行緒，具有很強的誤導性。筆者幾年前便察覺這個問題，但遊戲引擎已經完成，不敢貿然修改，以免影響比賽進度。此後也一直想推動相關重構，但因種種原因尚未實施。

苦思無果後，筆者也反覆與 [ChatGPT](https://chatgpt.com/)、[Google Gemini](https://gemini.google.com/) 等大型語言模型討論，但每項建議都存在上述一種或多種問題。其中甚至有一個相當抽象的題目：任務處理系統，讓使用者隨時提交任務並處理並行工作。這仍被筆者否決，因為需求不夠真實，只是先射箭再畫靶，刻意為知識點設計問題，缺少解決實際需求的感覺。

隨後，筆者又想到製作一個現實生活模擬器（大型語言模型也提出過類似構想），例如餐廳模擬器、印表機模擬器等，利用執行緒模擬點餐人流或印表機的列印任務。但問題是，現實生活中真的有這種需求嗎？這類模擬器有什麼用途？如果它是一款遊戲，為什麼不比照遊戲引擎依畫面更新率控制呢？因此，這個方案也被否決了。

第一道曙光是「平行編譯」。如同 `GNU Make`，編譯工作可以拆成多個任務，平行處理不同檔案。這是筆者想到的第一個看似可行的題目，但仍有許多問題。只有 C89 與 C++98 基礎的同學，真的能在短時間內理解詞法分析、語法分析等編譯原理，並實作出來嗎？如果由基礎程式碼提供完整編譯器、學生只負責呼叫，工作量又會太少，無法達到學習目標。更何況，平行編譯要如何自然地結合 gRPC？本機編譯根本不需要網路通訊；若改成類似 [Compiler Explorer](https://gcc.godbolt.org/) 的遠端編譯器，工作量又會過於龐大，GUI 必須處理多個檔案並將它們傳送至伺服器。編譯也不需要遠端 GPU 算力，而 GUI 本身又必須安裝 C\# 執行環境與應用程式；既然如此，何不直接安裝 C\# 編寫的本機編譯器？這項需求實在太不自然了。

想到這裡，筆者開始考慮放寬對實際需求的要求。編譯原理過於複雜，或許可以改成平行 JSON 解析器（雖然需求更不自然，但先不計較）。JSON 比程式設計語言簡單得多；只要基礎程式碼提供完整的詞法分析器與遞迴下降剖析架構，再用幾個小節說明如何編寫 LL(1) 剖析程式碼，學生應能自行完成其餘部分。

### 最終選題的確立

原以為 JSON 解析器就會成為最後的題目，但筆者仍覺得這項需求太不自然，實在難以正式採用。

轉機出現在 2026 年 6 月 3 日晚上。筆者腦中突然閃過一個念頭：與其解析 JSON，不如解析應用程式記錄，這不是更有意義嗎？筆者想起在 2026 年初看到的 [2025 年國際 AIOps 挑戰賽](https://competition.aiops.cn/)題目。該題提供雲端原生微服務應用程式產生的記錄，要求參賽者據此分析微服務呼叫鏈，並進行異常偵測與定位。以記錄為基礎的分析和異常偵測也是網路領域的一個研究方向。那麼，能否把賽題中最簡單的第一步——應用程式記錄預處理——獨立出來並大幅簡化，作為 workshop 的題目呢？

這在邏輯上完全合理。應用程式會產生多個記錄檔，平行讀取與解析相當常見。雖然讀取主要使用 I/O 資源，解析卻會使用 CPU；以多執行緒加速 CPU 密集型工作很有意義。

此外，在這個題目中導入 gRPC 也很自然。執行雲端服務的叢集通常位於遠端，而我們在本機透過用戶端控制遠端的記錄分析，甚至將結果視覺化，是相當合理的需求。隊式開發本來也需要在 Avalonia 介面中顯示資訊（例如檔案類型、記錄、人物動作與遊戲事件）；若設計一項顯示記錄內容的作業，也能為日後的隊式開發提供前瞻性訓練。

最終，我將雲端服務記錄處理系統作為本 workshop 的選題。

## 關於開發環境中的檔案讀寫問題

> 筆者：開發者 A

撰寫測試程式時，需要測試記錄檔的讀取，但這會引出一個問題。

從 Visual Studio 啟動程式時，應用程式會以可執行檔所在位置作為工作目錄，而該目錄通常應由 `.gitignore` 忽略。若資料集要納入 Git 版本控制，就不應放在這個目錄中。因此，以相對路徑指定資料集時便出現兩難：要在每次測試前手動複製資料集，還是在路徑中加入多層 `../../../`？前者繁瑣，後者更會破壞可攜性，讓相同程式碼在開發與正式環境中產生不同行為，嚴重影響後續開發。

幸好 MSBuild 提供了解決機制。只要在專案檔（`.csproj`）的 `<ItemGroup>` 元素中加入：

```xml
<None Include="..\dataset\*.log">
  <Link>dataset\%(Filename)%(Extension)</Link>
  <CopyToOutputDirectory>PreserveNewest</CopyToOutputDirectory>
</None>
```

編譯時，MSBuild 會自動將資料集複製到目標位置。`Include` 指定資料集相對於專案根目錄（`.csproj` 所在目錄）的路徑；`<Link>` 則指定資料集在輸出目錄中、相對於可執行檔的目標路徑。

於是問題被完美解決。

## 關於 AvaloniaUI 的網頁版與行動裝置版

## 關於編寫 WebAssembly 目標平台用戶端的額外難題

> 筆者：開發者 A

偶然發現 Avalonia 支援多平台用戶端，例如 Desktop（Windows、Linux、macOS）、Android、iOS 與 WebAssembly（可在瀏覽器中執行）。Android 需要處理許多簽署問題，筆者手邊又沒有 iOS 裝置，因此想試著同時支援 Desktop 與 WebAssembly（即 `LogAnalyzerClient.Browser` 專案），沒想到遇到了巨大困難。

第一個問題是 gRPC Web 與原生 gRPC 不同。gRPC Web 建立連線前，瀏覽器會先透過 HTTP/1.1 傳送 CORS 預檢要求 `OPTIONS`，原生 gRPC 則沒有這個步驟。因此，Agent 若只啟用 HTTP/2，gRPC Web 便無法連線；若同時啟用 HTTP/1.1 與 HTTP/2，原生 gRPC 又無法連線：

```csharp
builder.WebHost.ConfigureKestrel(options =>
{
    options.ConfigureEndpointDefaults(listenOptions =>
    {
        listenOptions.Protocols = HttpProtocols.Http2;	// gRPC Web 需要 HttpProtocols.Http1AndHttp2
    });
});
```

正因如此，同一個連接埠無法同時接受本機桌面用戶端與瀏覽器用戶端的連線，只能開啟兩個不同的連接埠，分別接受兩種用戶端。這可能會讓進行 workshop 的同學產生不必要的困惑，因此我決定不在 workshop 中加入瀏覽器平台；不過仍保留 `Browser` 專案，供有興趣的同學探索。

此外，若要支援瀏覽器平台，還必須設定 CORS；這屬於網站開發的內容，不適合放在隊式課程中。順帶一提，若要支援瀏覽器中的 gRPC Web，還要在 Agent 加入以下兩行：

```csharp
app.UseGrpcWeb();
app.MapGrpcService<AgentService>()
    .EnableGrpcWeb();
```

最耗費時間的兩個問題，是 Avalonia 與 `Grpc.AspNetCore` 無法共存於同一專案，以及 Desktop 和 Browser 建立 gRPC 用戶端的方式不同。

`LogAnalyzerRpc` 最初參考了 `Grpc.AspNetCore` 套件；但 Avalonia 專案參考它時，也會間接依賴 `Grpc.AspNetCore`，使兩者出現在同一專案中而無法相容，導致編譯失敗。經過仔細拆分後，`LogAnalyzerRpc` 只保留 `Google.Protobuf`、`Grpc.Tools` 與 `Grpc.Core.Api`（連 `Grpc.Core` 都不行，必須帶有 `.Api`）幾個套件。

下一個問題是版本選擇：究竟該使用哪個版本，才能盡可能確保與 `Grpc.AspNetCore` 2.80.0 相容？因此，我查看了 [gRPC for .NET v2.80.0 的原始碼](https://github.com/grpc/grpc-dotnet/tree/f22747c72676120b2bc69a1ba7c8bed995e29b1b)，從其中的[相依性設定檔](https://github.com/grpc/grpc-dotnet/blob/f22747c72676120b2bc69a1ba7c8bed995e29b1b/Directory.Packages.props#L35-L37)確認版本，並參考對應版本的套件：

```xml
<Project>
  <PropertyGroup>
    <GrpcDotNetPackageVersion>2.70.0</GrpcDotNetPackageVersion>
  </PropertyGroup>
  <ItemGroup>
    <PackageVersion Include="Grpc.Tools" Version="2.80.0" />
    <PackageVersion Include="Grpc.Core.Api" Version="$(GrpcDotNetPackageVersion)"/>
    <PackageVersion Include="Google.Protobuf" Version="3.31.1" />
  </ItemGroup>
</Project>
```

Desktop 與 Browser 建立 gRPC 用戶端的方式不同：Desktop 應使用 `Grpc.Net.Client` 套件；Browser 平台還需依賴 `Grpc.Net.Client.Web` 套件，而且兩者建立用戶端的方式也不相同：

```csharp
// Desktop
var channel = GrpcChannel.ForAddress(address);
var client = new LogAnalyzerAgentServiceClient(channel);

// Browser
var handler = new GrpcWebHandler(GrpcWebMode.GrpcWeb, new HttpClientHandler());
var channel = GrpcChannel.ForAddress(address, new GrpcChannelOptions()
    {
        HttpHandler = handler
    });
var client = new LogAnalyzerAgentServiceClient(channel);
```

因此，我使用工廠方法模式解決這項差異。

此外，全部流程跑通後，我發現部分 gRPC RPC 函式在呼叫時仍有問題，偶爾會呼叫失敗；但我暫時沒有精力釐清原因。因此，完成 Browser 平台支援的計畫暫時全面擱置。

## 關於問答題

> 筆者：開發者 A

既然已經有程式碼練習，為什麼還要安排問答題？主要有兩點考量。

第一點是大型語言模型的使用。Vibe coding 現在十分流行，學生很容易在缺少思考的情況下依賴它。因此，每一節末尾都設有關於 AI 使用的問答題，引導同學評估模型產生內容的品質。Vibe coding 出現時間尚短，筆者也無法確定它對程式設計初學者的影響；這些問題同時可視為一項小型調查，用來了解大型語言模型如何影響新手學習。

第二點是基礎程式碼本身。它已實作大部分輸入、輸出與基礎設施；第一章尤其完整，同學只需補上少量程式碼即可完成。這項設計是為了照顧剛接觸 .NET 的同學，並讓基礎程式碼隨章節逐步減少，以配合學習曲線。前面的基礎章節也支撐後續內容，因此需要盡量避免學生在早期犯下過大的錯誤，或因無法完成而中斷後續學習。缺點是，只補上少量程式碼並不能證明學生真正理解整體架構。因此，部分問答題會針對基礎程式碼的實作提問，引導同學仔細閱讀。
